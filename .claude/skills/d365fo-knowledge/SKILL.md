# D365FO knowledge — this repo's own corpus

This repository *is* the source of the D365FO/X++ knowledge corpus. When a task
here touches what the tool teaches — a scaffolder's output, a validator rule, a
topic file — the corpus is the reference, not your training data.

## Where it lives

| Form | Path | Use |
|---|---|---|
| Source of truth | `skills/_source/<id>.md` | edit here, always |
| Claude/Anthropic variant | `skills/anthropic/<id>/SKILL.md` | generated; read as a skill |
| Copilot variant | `skills/copilot/<id>.instructions.md` | generated |
| `d365fo-cli` agent skill | `skills/d365fo-cli/` | generated regions + hand-written shell |
| Embedded in the binary | `D365FO.Core.Knowledge.KnowledgeBase` | served by `d365fo knowledge` |

Everything but `skills/_source` is generated by `python scripts/emit-skills.py`.
**Never edit a generated file** — CI fails on drift.

## Reading it

```sh
d365fo knowledge list --output json
d365fo knowledge search "how do I post a voucher" --output json
d365fo knowledge get posting-and-financials --section "2. Posting"
```

Prefer `search` → `get --section` over whole topics; a full topic runs to a few
thousand tokens. The same corpus is what `get_knowledge` serves over MCP.

## Changing it

1. Edit `skills/_source/<id>.md`.
2. `d365fo knowledge audit --output json` — resolves every named AOT type/API
   against the symbol index and runs every code example through the offline BP
   validator. **A knowledge edit is not done until this is clean.**
3. On a machine with a full standard index:
   `d365fo knowledge audit --capture` and commit
   `eval/knowledge-audit.snapshot.json`. CI has no index and gates on that
   snapshot, so an un-audited edit cannot ship.
4. `python scripts/emit-skills.py` and commit the regenerated variants.

Reviewed exceptions (kernel types that exist only in the AOS binaries, the
corpus's own example namespace, intentional wrong-vs-right demos) live in
`eval/knowledge-audit.allow.json`, each with a written reason.

## The rule canon

Rule blocks fenced with `<!-- canon:<id> -->` inside a topic are the single
source for the X++ rules published by `d365fo agent-prompt`, by the MCP
`initialize` instructions, and by `skills/d365fo-cli/SKILL.md`. Change the rule
in the topic that owns it — never in a consumer.

## When writing D365FO facts anywhere in this repo

Ground them. `d365fo get class <Name> --output json`, `d365fo search any <Name>`,
`d365fo get table <Name>`. A plausible-sounding framework name is the most common
defect in this domain: `SysRunnable`, `SysTelemetry`, `FeatureClassAttribute`,
`GlobalAddressBookHelper` and `AggregateFunction` all read as real and none exist.
